# かけよ Next.js 移行：機能差分リスト（旧Vue版 → Next版）

- **作成日**: 2026-09-22
- **目的**: Nuxt/Vue 版で存在した機能が Next.js 移行に伴い「欠落・後退・リンク切れ・仕様差」を起こしていないかを網羅調査し、別セッションでの対応推進のための **積み残しリスト** として残す。
- **調査範囲**: 旧 `kakeyo/`（pages / components / layouts / composables / api/supabase / utils）× Next `kakeyo/nextjs/src/`（app / features / lib）を、**UI操作単位・API/RPC関数単位・utils/定数単位・デモ/認証・仕様書(fe-screens/be-api)基準** の6観点で突き合わせた。
- **前提文書**: [移行方針確定書.md](移行方針確定書.md) / [移行手順書.md](移行手順書.md) / 仕様書 `../new/docs/replace/*.md` / DDL・RPC `../docs/database/*.md`
- **凡例**: 🔴=明確な欠落・バグ（要対応） / 🟡=UI/操作性の後退・仕様差 / 🔵=要確認（確証が持てず精読/実機確認が必要） / ✅=移植済み（むしろ堅牢化された参考情報） / **✔=本対応で解消済み**

> **総括**: **API/RPC の関数レベルでは欠落はほぼ無く**、むしろ scope 検証・`$transaction` 化・BigInt 境界変換など**堅牢化**されている。欠落・後退は主に **①画面の導線（record 編集・plan/reminder クリック・inquiry）**、**②一部の細かいドメインロジック/定数（MAX_PRICE 上限・autoLink・按分レート・DaysByMonth）**、**③意図的に別チケット送りされた機能（アカウント削除・精算レート按分・メール確認）** に集中する。

## A. 🔴 明確な欠落・リンク切れ（要対応）

### A-1. record（実績記録）の編集導線が全面欠落 ★最重要 ✔ 対応済
- **症状**: 記録の「編集・削除」に到達する手段が実質すべて機能しない。移行で最も影響の大きい欠落。
- **根本原因（Next版）**:
  - [note/page.tsx](../nextjs/src/app/(private)/note/page.tsx) の `searchParams` 型が `{ plannedRecordId?: string }` のみで、**`RECORD` クエリを一切読まない**。
  - `NoteRecordForm` に `editing` プロパティを渡す口はある（[note-record-form.tsx:52](../nextjs/src/features/record/components/note-record-form.tsx)）が、page.tsx が planned しか渡していない。
  - **record 単体取得サービス（`getRecordForEdit` 相当）が [record/server/services.ts](../nextjs/src/features/record/server/services.ts) に存在しない**。
- **連鎖するリンク切れ**:
  - records 明細画面は `/note?RECORD=<id>` へ遷移するが（[records-screen.tsx:109](../nextjs/src/features/summary/components/records-screen.tsx)）、**飛んでも新規入力フォームが開くだけ**。
  - calendar の日別 record リストも編集ボタンが無い（[day-record-list.tsx](../nextjs/src/features/calendar/components/day-record-list.tsx)、TODO 明記）。
- **旧の該当**: `pages/note.vue:353-371`（`?key=RECORD` で routerParam から record を受けプリフィル、「変更」＋削除ボタン）、`RecordCard.vue`（ペンアイコン→ `goRecordEditPage`）。
- **対応方針メモ**: record 単体取得サービス追加 → note/page.tsx で `?RECORD=` を読み `editing` を渡す → records/calendar の遷移リンクと接続。BigInt PK の `Number()` 境界変換を忘れない。編集時の「定期由来 record は同月のみ変更可」は**すでに service 層に移設済み**（`upsertRecord` 内）なので UI 側の再実装は不要。

### A-2. calendar の plan / reminder イベントクリックが未接続 ✔ 対応済
- **症状**: カレンダー上の予定・リマインダーをクリックしても何も起きない。既存 plan の**編集・削除への到達手段が消失**。
- **根本原因**: `MonthCalendar` は `onEventClick` フックを持つが [calendar-screen.tsx](../nextjs/src/features/calendar/components/calendar-screen.tsx) がそれを渡していない（TODO 明記）。旧の `PlanCard` / `ReminderCard` 相当のコンポーネントも未実装。
- **旧の該当**: `pages/calendar.vue:324-389`（`showEvent` 分岐で PlanCard/ReminderCard 表示、`goPlanEditPage` 編集、`deleteReminderPlan` 削除）。
- **補足**: plan 画面自体は編集可（`PlanForm` が `editing` prop を持つ）だが、**PlanScreen / plan/page.tsx が `editing` を渡していない**（[plan-screen.tsx](../nextjs/src/features/plan-reminder/components/plan-screen.tsx) は `initialDate` のみ）。calendar 統合待ちのコメントあり。A-2 と一体で対応する。

### A-3. アカウント削除（deleteUser）機能が未実装 📋 保留（設計判断要）
- **症状**: 退会（アカウント削除）ができない。
- **旧の該当**: `components/setting/General.vue:29,48-58`（2段階の同意チェックボックス「消しても後悔しません」→「復元を求めません」を経て `useFirebase.deleteUser`）。
- **Next版**: 設定「その他」タブは**ログアウトのみ**（[general-tab.tsx](../nextjs/src/app/(private)/setting/general-tab.tsx) に「本移行では省略・TODO(別チケット)」と明記）。
- **注記**: Supabase Auth 側の退会フロー（Auth ユーザ削除＋関連データの扱い）が未確定のため意図的に保留。**設計判断が必要な項目**。
- **→ 保留 TODO へ集約**: 設計論点・着手前チェックリストは [保留TODO_設計判断要.md](保留TODO_設計判断要.md) T-1 にまとめた（別セッションで方針確定後に着手）。

### A-4. 問い合わせ（inquiry）への画面内導線が消失 ✔ 対応済
- **症状**: `/inquiry` ページ・proxy 許可（[proxy.ts:14-15](../nextjs/src/proxy.ts)）はあるが、**アプリ内のどこからもリンクされていない**（`grep` で `/inquiry` への Link/href 0 件）。URL 直打ちのみ到達可。
- **旧の該当**: `layouts/default.vue:170-174`（ハンバーガーメニュー内 `inquiryItem`。ログイン前後問わず常時到達可能）。
- **原因**: 旧のハンバーガーメニュー（`v-navigation-drawer`）そのものが Next版で廃止されたため（→ B-1）。

### A-5. メモ内 URL の自動リンク（autoLink）が欠落 ✔ 対応済
- **症状**: plan / reminder のメモに書いた URL がリンクにならない（プレーンテキスト表示）。
- **旧の該当**: `utils/string.ts:35` `autoLink()` を `components/PlanCard.vue:27` / `components/ReminderCard.vue:25` が `v-html` で使用。
- **Next版**: `autoLink` 相当が存在しない（`grep` 0 件）。※ PlanCard/ReminderCard 自体が未実装（A-2）なので、それらの再実装時に併せて対応する。

### A-6. 金額上限（MAX_PRICE = 1000万円）バリデーションが欠落 ✔ 対応済
- **症状**: 金額入力に上限がなく、桁溢れ・BigInt 境界級の値を許してしまう。
- **旧の該当**: `utils/constants/index.ts:14` `MAX_PRICE = 10000000` を `components/NotePrice.vue:78,85` の入力ロジックで超過抑止（`model*10+num < MAX_PRICE`）。
- **Next版**: 共有 [price.ts](../nextjs/src/lib/shared/domain/price.ts) の `priceSchema` は `int().nonnegative()` のみで **`.max()` が無い**。
- **対応方針メモ**: `priceSchema` に `.max(10_000_000)`（境界の含む/含まないは旧の `< MAX_PRICE` に合わせるか要検討）相当を追加すれば、金額を持つ全レーン（record / planned_record / short_cut / bank_balance）に一括で効く。**凍結資産のため変更はオーケストレータ承認が必要**（[移行手順書.md](移行手順書.md) 鉄則1）。

### A-7. summary 精算タブ：按分レート選択＋自動精算額算出フローが後退 ✔ 対応済
- **症状**: 「誰がいくら渡す/受け取る」の**自動計算という中心機能**が失われ、金額の手入力に置き換わっている。
- **旧の該当**: `components/SummarySettlement.vue`（3ステップ Stepper：開始→分類→完了、`SettlementSelectRateDialog.vue` でレート 10:0〜0:10 を record ごとに割当 → レート別「合計/現状/期待」算出 → 差額から自動で「◯◯円のお渡し/受け取り」提示 → 精算 record 自動作成＋精算済み化）。関連定数 `RATE_LIST` / `RATE_LABEL_LIST` / `RATE_COLOR_LIST` も旧 `utils/constants` にあった。
- **Next版**: [summary-settlement.tsx](../nextjs/src/features/summary/components/summary-settlement.tsx) は**チェックボックスで対象選択＋方法/金額/方向を手入力**する簡易フロー（「レート按分 UI は将来拡張」とコメント明記）。`RATE_*` 定数も未移植。
- **補足**: record CRUD レベルの `createSettlementRecord` / `settleRecords` は実装済み。UI のレート按分・差額自動算出ロジックのみ欠落。**仕様の中核なので優先度高め**。

## C. 🔵 要確認（精読 or 実機確認で確定させるべき灰色項目）

### C-1. method の `both`（精算方法）グループ振り分けの差 ★潜在バグ
- 旧 `getMethodList` は `both.self: []`（常に空）で精算 method を **pair のみ**に寄せていた。
- Next `groupMethodList`（[type-method/grouping.ts](../nextjs/src/features/type-method/grouping.ts)）は `both.self` / `both.pair` の**両方へ `isPair` 判定で振り分ける**。
- → 精算 method が self 側に表示されうる。**旧と挙動が異なる可能性**。精算方法の一覧 UI で要確認。

### C-2. リマインダーの「日」選択が月末非対応（DaysByMonth 欠落）
- 旧 `utils/time.ts` `DaysByMonth(year, month)` で月ごとの日数に応じた選択肢を生成（ただし旧は**うるう年非考慮＝2月28日固定**）。
- Next `reminder-dialog.tsx` は**常に 1〜31 固定**（コメントで「厳密な月末判定はしない」）。2/30 等の不正日を選べる差。
- 別途、reminder-condition.ts の `daysInMonth` は**うるう年考慮**で、旧 `DaysByMonth`（非考慮）と非同値。用途は違うが要整理。

### C-3. 色ネストの平坦化によるフィールド落ち
- `getBankList`: 旧 `colorClassifications:{id,name}` → Next `colorName` のみ（色 id ネスト落ち）。
- `getShortCutList`: 旧は type/method **両方**に色ネスト → Next は **type 色のみ**、method 色・`userId`/`pairId` が落ち。
- `getBankBalanceList`: 旧はセル単位に `color` → Next スナップショットは色を持たない（口座列側で解決の設計）。
- → いずれも表示等価の可能性が高いが、色分け要件上問題ないか要確認。

### C-4. `getPairId` の重複防御の欠落（軽微）
- 旧 `api/supabase/user.ts` は pairs が複数件ヒットで「DB の状態がおかしい」エラー。
- Next [auth/server/pair.ts](../nextjs/src/features/auth/server/pair.ts) は `findFirst` のため**複数件でも先頭を黙って採用**。データ不整合の検出が緩い。

### C-5. swap 系 DB 関数と `$transaction` 置換の等価性
- 旧 `swap_type` / `swap_sub_type` / `swap_method` / `swap_plan_type` / `swap_planned_record`（DB 関数）→ Next は `prisma.$transaction([update, update])` の2行 sort 交換。
- DB 関数本体（`docs/database/functions.md`）に**単純 sort 交換以外のロジック（連番振り直し等）が含まれる場合、非等価**になりうる。関数定義の確認で確定させる。

### C-6. reminder の `all` グルーピング保持
- 旧 `getReminderList` は self/pair に加え `all` も返す（通知ベルが利用）。Next `groupReminderList` が `all` 相当を保持しているか要確認（[plan-reminder/grouping.ts](../nextjs/src/features/plan-reminder)）。※通知ベル自体は SSR で `date <= today` 抽出して動作しているので実害は薄い可能性。

### C-7. リマインダー次回日付の月末 clamp の厳密一致
- 旧は dayjs の `.add(month,'month')`（月末自動繰上げ：1/31+1ヶ月→2/28）。Next `calcNextReminderDate`（[reminder-condition.ts](../nextjs/src/features/plan-reminder/domain/reminder-condition.ts)）は clamp を明示実装。**境界の厳密一致**を Vitest 等で確認したい。

### C-8. 集計の月末境界（包含判定）
- 旧 `ConvertYearMonthObjToEndOfMonthDatetime`（月末23:59:59 等）→ Next は「翌月初 未満（gte..lt）」/「endOfDay（gte..lte）」方式に再設計。月末最終秒のレコード取りこぼしが無いか要確認（[date.ts](../nextjs/src/lib/shared/domain/date.ts) と各 period test）。

### C-9. デモで見えるデータ量・範囲の縮小
- **旧デモは実 DB の本物のデモデータを読む**（取得系にデモ分岐なし、書き込みのみ no-op）。`DEMO_USER_INFO.PAIR_ID=2` の実データが複数月分見えていた。
- Next デモは**静的モックを注入**（各 feature `server/demo.ts`）。モックに書いた分（各1〜3件程度）しか見えない。
- 特に **calendar の月次収支（getMonthSum）はデモで `withDemoRead(0)` により常に 0 固定**（[calendar/server/services.ts:36](../nextjs/src/features/calendar/server/services.ts)）。デモのカレンダー月サマリが 0 表示になる。デモ体験の充実度が旧より縮小していないか要確認。

### C-10. メール確認（本人確認）フローの欠落
- 旧 `useFirebase`：サインアップ時 `sendEmailVerification`、ログイン時 `emailVerified===false` を弾き「本人確認メールの URL で認証を」表示、`IsInWhiteList` 例外。
- Next版：これらが一切存在しない（`grep` 0 件）。新規登録 UI 自体が旧でも無効化されているため運用上の影響は限定的だが、**ログイン時の未認証弾き**が Supabase Auth 側設定で代替されているか要確認。
- **→ 保留 TODO へ集約**: 確認観点は [保留TODO_設計判断要.md](保留TODO_設計判断要.md) T-2 にまとめた（Supabase の Confirm email 設定で足りる可能性が高い）。

### C-11. サポート範囲の年ガードの欠落（軽微）
- 旧 `PrevYear`/`NextYear` 系は 2000 年以前/2100 年以降を alert で拒否。Next `shiftMonth` にこのガードは無い。実害は小さいが仕様差。

### C-12. その他の細かい定数/ヘルパの集約喪失（軽微）
- `typeAndSubtype`（type ー subType の ` ー ` 連結ヘルパ）→ Next は個別に扱い、連結ヘルパ未発見。
- `MONTH_LABELS`（`'12(月)'` 等のラベル）、`COLOR_LIST`（色の順序付き配列）、`SettlementRecord`（name:'精算'/color:'yellow'）、`APP_NAME` などの定数がリテラル散在化。表示に影響が出ていないか要確認。

## D. ✅ 移植済み・堅牢化（参考：欠落ではない設計変更）

対応漏れではないが、旧と挙動が変わる/強化された点。**「消えた」と誤認しやすいので記録**。

- **API/RPC の全関数に対応実装あり**（record/plan/reminder/planned-record/bank/memo/shortcut/type/method/master）。フィールド落ちは C-3 の色ネストのみ。
- **scope 徹底・IDOR 防御**: 全取得系が `buildScopeWhere`/`buildOwnerScopeWhere`、更新/削除は where に scope AND＋件数チェック。旧より安全。`getPairedRecordList` は旧が全ペア分を引きうる緩実装だったのを Next が正しく絞り込み（実質バグ修正）。
- **`$transaction` 原子化**: insertReminder / deleteReminder / checkReminder / 各 swap。
- **record_type（0/5/10/15）分岐**は `resolveRecordType` に集約・**Vitest 保護**で旧と同値。
- **JST 日付**は「+9h して toISOString」独自方式を廃止し dayjs.tz（Asia/Tokyo 明示）へ。SSR 時刻ズレ対策で改善。
- **定期実体化（post_records）** は閲覧駆動の副作用 INSERT を廃し **Vercel Cron 日次** へ移設（多重 INSERT 問題の根本解決、[移行方針確定書.md](移行方針確定書.md) §7）。SQL は逐語移植。**ただし「今月を開いた瞬間に定期が入る」即時性は失われる**（B/C 的な認識が必要）。
- **金額パース**は `priceSchema`（全角/カンマ正規化＋非負整数、Vitest 付き）に集約（上限だけ欠落＝A-6）。
- **トースト2系統**（`FormActionResult.toast` / `setFlashToast`）、**デモ注入**（`withDemoRead`/`withDemoWriteVoid`）は AGENTS.md 準拠で整備済み。
- 認証操作：signIn / signOut / デモログイン / パスワード再設定は対応済み。新規登録は旧も無効化のため等価。
