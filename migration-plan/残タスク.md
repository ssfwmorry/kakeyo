## 1. 🔴 アカウント削除（退会）

### 現状

- Next 版の設定「その他」は**ログアウトのみ**（[setting-screen.tsx](../src/features/setting/components/setting-screen.tsx) で「アカウント」行を退会フロー確定まで出していない）。
- 旧 Vue 版（`components/setting/General.vue`）は 2 段階の同意チェック
  （「消しても後悔しません」→「開発者にデータの復元を求めません」）の後、
  Firebase Auth のユーザ削除**だけ**を行い、records / pairs 等の業務データには触れていなかった。

### 着手前に決めること

1. **auth.users の削除方法**
   Supabase Auth のユーザ削除は service_role の `auth.admin.deleteUser(uid)` が必要。
   Server Action + service_role キー（`lib/server/env.server.ts` に隔離、クライアントへ出さない）で行う。
2. **関連データの扱い（最重要）**
   ペア家計簿のため、退会ユーザの records / planned_records / bank / pairs を
   物理削除するか・匿名化するか・ペア相手のデータ整合をどう保つかを決める。
   共有 record（record_type=5/10/15）や pairs 行を消すと相手の家計が壊れる。
   FK の on delete 挙動（CASCADE / SET NULL / RESTRICT）を [docs/database/tables.md](../docs/database/tables.md) で確認する。
   旧実装踏襲なら Auth ユーザ削除のみだが、「退会したのにデータが残る」状態になる。
3. **同意 UX**: 旧の 2 段階チェックを踏襲するか、`AlertDialog` による確認に置き換えるか。

### 実装イメージ（決定後）

- `general-tab.tsx` に退会セクションを追加。
- `deleteUserAction`（Server Action・service_role）で「関連データ処理 → `auth.admin.deleteUser` → signOut → /login へ redirect + flash」。
- public スキーマへの書き込みを伴うため、実行前にユーザ承認が必要（AGENTS.md）。

### チェックリスト

- [ ] FK on delete 挙動を DDL で確認（records / pairs / planned_records の user_id 参照）
- [ ] 関連データ方針（物理削除 / 匿名化 / ペア整合）を確定
- [ ] service_role キーのサーバ限定管理を設計

## 2. 🔵 メール確認（本人確認）フロー

- 旧 Vue 版はサインアップ時に `sendEmailVerification`、ログイン時に `emailVerified === false` を弾いていた。
  Next 版にはどちらも存在しない（新規登録 UI 自体が旧でも無効化されていたため運用影響は限定的）。

## 3. 📋 ショートカットの `pairId`（カード保持値 → セッション再導出）

- 旧 Vue 版は `short_cuts` 行の `pair_id` をそのまま使って record を作っていた。
  Next 版は `ShortCutListItem` に `pairId` を持たせず、Server Action がセッションの `pairId` から導出する。
- 差が出るのは、ペア解消 / 再ペア後に**古い `pair_id` を持つショートカット行**が残っている場合のみ。
  旧＝古いペアで記録される、新＝常に現在のペアに正規化される。
- **推奨**: Next 版の挙動（セッション再導出）を正として確定。AGENTS.md の
  「`userUid`/`pairId` はセッションから確定し、クライアント値を信用しない」と整合し、実装ゼロ。
  旧挙動に戻すなら、行の `pair_id` をサーバ側で再取得・検証する形にしなければならない。

- [ ] セッション再導出（現状維持）で確定するか判断
- [ ] 確定する場合、pairId 変動後に残る古いショートカット行の扱い（洗い替え / 放置 / 作り直しを促す）を決める
