## T-1. 🔴 アカウント削除（退会 / deleteUser）— 差分リスト A-3

### 現状

- **Next版**: 設定「その他」タブは**ログアウトのみ**（[general-tab.tsx](../nextjs/src/app/(private)/setting/general-tab.tsx) に「本移行では省略・TODO(別チケット)」と明記）。退会導線なし。
- **旧Vue版**: `components/setting/General.vue`。2段階の同意チェックボックス
  （「消しても後悔しません」→「開発者にデータの復元を求めません」）を経て、
  `useFirebase.signOut()` → `useFirebase.deleteUser()`（**Firebase Auth のユーザ削除のみ**）→ login へ遷移。
  ※ 旧実装は Firebase Auth 上のユーザを消すだけで、**records / pairs 等の業務データの削除・匿名化には触れていない**。

### 設計判断が必要な論点（着手前に決めること）

1. **auth.users の削除方法**
   - Supabase Auth のユーザ削除は管理者権限（service_role）の `auth.admin.deleteUser(uid)` が必要。
     クライアント/通常セッションからは実行不可 → **Server Action + service_role キー**（サーバ限定・環境変数）で行う設計になる。
   - service_role キーの取り扱い（`lib/server/env.server.ts` 相当に隔離。クライアントへ絶対に出さない）。
2. **関連データの扱い（最重要・法的にも関わる）**
   - ペア（夫婦）家計簿という性質上、退会ユーザの records / planned_records / bank / pairs を
     **物理削除するか / 匿名化するか / ペア相手のデータ整合をどう保つか**を決める必要がある。
     - 例: ペア相手が残る場合、共有 record（record_type=10/5/15）や pairs 行を消すと相手の家計が壊れる。
   - FK 制約（records.user_id → auth.users 等）の on delete 挙動（CASCADE / SET NULL / RESTRICT）を
     DDL で確認・確定する（[docs/database/tables.md](../docs/database/tables.md)）。
   - 旧実装が業務データを消していない＝**現行踏襲なら Auth ユーザ削除のみ**だが、
     それだと「退会したのにデータが残る」状態になる。移行を機に方針を決めるべき。
3. **UX（同意フロー）**
   - 旧の 2 段階同意チェックを踏襲するか、shadcn の AlertDialog による確認に置き換えるか。
   - ドロワー廃止（差分リスト B-1）に伴い、退会導線は設定「その他」タブ内で完結させる想定。

### 対応方針メモ（決定後の実装イメージ）

- `setting/general-tab.tsx` に退会セクション（2 段階同意 or AlertDialog）を追加。
- `deleteUserAction`（Server Action・service_role 使用）で
  「関連データ処理（方針次第）→ `auth.admin.deleteUser` → signOut → /login redirect + flash」。
- **public スキーマへの書き込み（削除）を伴うため、実行前にオーケストレータ承認が必要**
  （[AGENTS.md](../nextjs/AGENTS.md) 「public スキーマの DB 書き込みは許可制」）。

## T-2. 🔵 メール確認（本人確認）フロー — 差分リスト C-10

### 現状

- **旧Vue版（`useFirebase`）**: サインアップ時に `sendEmailVerification`、
  ログイン時に `emailVerified === false` を弾いて「本人確認メールの URL で認証を」表示、`IsInWhiteList` で例外扱い。
- **Next版**: これらが**一切存在しない**（`grep` で 0 件）。
  新規登録 UI 自体が旧でも無効化されているため運用上の影響は限定的。

### 設計判断が必要な論点

1. **ログイン時の未認証弾き**が Supabase Auth 側の設定（Confirm email 有効化）で代替されているかを確認する。
   - Supabase の Auth 設定で "Confirm email" が ON なら、未確認ユーザはそもそもセッションを持てず、
     アプリ側での明示的な弾きは不要になる可能性が高い（=実装不要で確定できるかもしれない）。
2. 新規登録フローを Next 版で復活させるかどうか（旧は無効化済み）。復活させる場合のみ
   `sendEmailVerification` 相当（Supabase の signUp + email confirm）が要る。

### 対応方針メモ

- まず **Supabase プロジェクトの Auth 設定（Confirm email / ホワイトリスト運用）を確認**し、
  「アプリ側実装が要るのか、設定で足りるのか」を切り分ける。多くの場合は Supabase 設定側で完結する見込み。
- 設定で代替できていれば **本項目は「対応不要（設定で担保）」としてクローズ**できる。

## T-3. 📋 ショートカットの `pairId` が「カード保持値」→「セッション再導出」に設計変更 — 差分リスト C-3b

### 現状

ショートカット（`short_cuts`）からワンタップで record を作る際の **ペア判定の出どころが新旧で異なる**。

- **旧Vue版**: `getShortCutList` が行の `pair_id` を**そのまま返し**（[api/supabase/shortCut.ts](../api/supabase/shortCut.ts)）、
  記録作成時に**カードが保持している値**を使っていた（[pages/calendar.vue:542-543](../pages/calendar.vue)）。

  ```js
  isPair: shortCut.pairId !== null,
  pairId: shortCut.pairId,
  ```

- **Next版**: 戻り型 `ShortCutListItem`（[short-cut.ts](../nextjs/src/features/memo-shortcut/server/repositories/short-cut.ts)）に
  **`pairId` / `userId` を含めない**。記録作成は Server Action が `requireAuth()` の
  セッションから導出する（[calendar/actions.ts:57-64](../nextjs/src/features/calendar/actions.ts)。
  `isPair` は `recordType !== RecordType.self` で判定）。
  取得自体は個人専用テーブルとして `buildOwnerScopeWhere` を通しており、scope 上の問題はない。

### 差が出る条件（＝設計判断が要る理由）

**行の `pair_id` と現在のセッションの `pairId` が食い違うとき**に挙動が分岐する。具体的には:

- ペア解消 / 再ペア設定で `pairId` が変わった後、**古い `pair_id` を持つショートカット行**が残っているケース。
  - 旧 = 行の古い `pair_id` で記録（今のペアとズレた record ができうる）
  - 新 = 常に現在のセッションのペアで記録（今のペアに正規化される）
- ペア無しになった後に、ペア前提で作られたショートカットを押したケース。

**Next 版の挙動（セッション再導出）の方が一貫性・安全性は高い**と考えられるが、
「過去に作ったショートカットの意味が後から変わる」ことをプロダクトとして許容するかは判断が要る。

### 判断が必要な論点

1. **セッション再導出を正とするか**（＝現状の Next 実装を確定とし、本項目をクローズするか）。
2. 旧挙動（行の `pair_id` 尊重）を残す場合、`ShortCutListItem` に `pairId` を復活させ、
   Server Action 側でカード由来の値を受け取る設計に戻す必要がある。
   ただし**クライアント由来の値で scope を決めることになる**ため、
   AGENTS.md の「`userUid`/`pairId` はセッションから確定し、クライアント値を信用しない」と正面衝突する。
   → 復活させるなら「行の `pair_id` をサーバ側で再取得して検証する」形にする必要がある。
3. `pairId` 変動時に**既存ショートカット行をどう扱うか**（移行時に洗い替える / 放置する / 作り直しを促す）。

### 対応方針メモ

- 実質的には **1 を選んで「現状維持で確定」とするのが素直**（scope 方針とも整合し、実装ゼロ）。
- その場合でも 3（`pairId` 変動時に残る古い行）の扱いだけは決めておくと、運用時の混乱を避けられる。

## T-4. 📋 デモで見えるデータ量・範囲の縮小 — 差分リスト C-9

### 現状

- **旧Vue版のデモ**: 取得系にデモ分岐が無く、**実 DB の本物のデモデータ**を読んでいた
  （書き込みのみ no-op）。`DEMO_USER_INFO.PAIR_ID=2` の実データが**複数月分**見えていた。
- **Next版のデモ**: 各 feature の `server/demo.ts` から**静的モックを注入**（`withDemoRead`）。
  モックに書いた分（各 1〜3 件程度）しか見えない。
- 特に **calendar の月次収支（`getMonthSum`）はデモで常に 0 固定**
  （[calendar/server/services.ts:32-34](../nextjs/src/features/calendar/server/services.ts) で `withDemoRead(session.isDemo, 0, ...)`）。
  デモのカレンダー月サマリが 0 表示になる。

### 差の要点

**DB 非依存というアーキテクチャ上の判断は正しい**（[デモモードDB非依存化.md](999残タスク_デモモードDB非依存化.md) でさらに
認証層まで DB 非依存にする方針が確定済み）。論点は安全性ではなく、
**「不特定多数に見せるデモとして、体験の説得力が足りるか」**という充実度の話。

- 月次収支 0 固定は、家計簿アプリのデモとして**主要な訴求点が伝わらない**可能性がある。
- 複数月を行き来しても中身が変わらないため、カレンダー/集計/推移グラフの価値が伝わりにくい。

### 判断が必要な論点

1. **デモに求める体験レベルを決める**: 「画面が壊れずに一通り触れれば十分」か、
   「実際の家計簿らしい厚みのあるデータを見せたい」か。
2. 厚みを持たせる場合、**モックデータをどこまで作り込むか**
   （複数月 × record / planned_record / bank 残高推移 / 集計の整合を取る必要がある。
   集計値を手で置くのか、モック record から算出するのか）。
3. `getMonthSum` の 0 固定を**モック record から算出した値に置き換えるか**
   （置き換えるならデモ用の集計を純粋関数で持つ形になる。DB には触れない）。
4. [デモモードDB非依存化.md](999残タスク_デモモードDB非依存化.md) の「ペアあり / ペアなし」2 モードと
   **どう組み合わせるか**（solo モード用のモックも要るか）。

### 対応方針メモ

- **先に [デモモードDB非依存化.md](999残タスク_デモモードDB非依存化.md) の実装を終えてから着手するのが順当**。
  あちらは「モック資産（約 600 行）は無変更」が前提なので、先にモックを増やすと二重作業になりうる。
- 実装する場合も **DB には一切触れない**（モックの拡充のみ）方針は維持する。
