## 0. 背景と動機

デモアカウントは**不特定多数からアクセスされる**運用を想定する。そのため、デモの全ライフサイクル
（ログイン → 各画面表示 → 操作）で **Supabase Auth・DB に一切アクセスさせない**ことをゴールとする。

### 現状（変更前）に残っている DB / バックエンドアクセス経路

現状はアプリのデータ層こそ安全（取得=モック / 更新=no-op）だが、**認証層が DB / Supabase Auth を叩いている**。

| 経路 | 現状の実装 | 不特定多数アクセス時の懸念 |
| :--- | :--- | :--- |
| デモログインの認証 | [demoLoginAction](../nextjs/src/features/auth/actions/login-actions.ts) が実 Supabase `signInWithPassword` を叩く | Supabase Auth への**認証リクエストが青天井**（レート制限・課金・アカウントロック）。実在アカウント + パスワードの運用コスト |
| セッション導出（毎リクエスト） | [session.ts](../nextjs/src/features/auth/server/session.ts) の `getSessionData` が `getUser()`（Auth 往復）+ `findUserBySupabaseUid`（**DB**）+ `getPairId`（**DB**） | デモの**全リクエストで DB に 2 クエリ**。ここが最大の穴 |
| アプリのデータ取得 | サービス層が [withDemoRead](../nextjs/src/features/auth/server/demo.ts) でモック返却 | DB に触れない（OK・変更不要） |
| アプリのデータ更新 | [withDemoWriteVoid](../nextjs/src/features/auth/server/demo.ts) で no-op 成功 | DB に触れない（OK・変更不要） |
| **色マスタ取得**（2026-09-23 追記） | [getColorClassificationList](../nextjs/src/features/master/server/repositories/colorClassification.ts) が **`withDemoRead` を通らず** `prisma.colorClassification.findMany` を直に叩く。[setting/page.tsx](../nextjs/src/app/(private)/setting/page.tsx) / [bank/page.tsx](../nextjs/src/app/(private)/bank/page.tsx) が page から直接呼ぶ | **デモで /setting・/bank を開くと実クエリが飛ぶ**。全ユーザ共通の静的マスタ（色名のみ）で scope 非依存・情報漏洩リスクはなく、`cache()` 済みで 1 リクエスト 1 回だが、「DB に一切触れない」ゴールには反する → §2 #8 で塞ぐ |

→ **塞ぐべきは主に認証層。ただしアプリ層にも色マスタ 1 経路の穴がある**（当初「アプリ層は既に安全」と記載していたが、
2026-09-23 のコード突合で上記 1 件が判明したため訂正）。

## 1. 確定方針（🟢）

### 1-A. デモを「Supabase を経由しない純粋なフロントエンドセッション」にする

```
【変更後】
 デモログイン ──> 署名付きデモ Cookie をセットするだけ（Supabase を一切叩かない）
 各リクエスト ──> getSessionData 先頭でデモ Cookie を検証 → DB 照会せず固定 SessionData を返す
 データ取得/更新 ──> withDemoRead / withDemoWriteVoid（配線はそのまま流用）
```

- デモログイン = **署名付きデモ Cookie をセットするだけ**。Supabase `signInWithPassword` は呼ばない。
- `getSessionData()` は**先頭でデモ Cookie を検証**し、有効なら **DB 照会を一切せず固定 `SessionData`** を早期 return する。
- `withDemoRead` / `withDemoWriteVoid` の**土台と各サービス層の配線は変更しない**。`isDemo=true` が立てば
  従来どおりモック注入・no-op が効く。
- ~~各 feature の `demo.ts`（モックデータ・約 600 行）は一切変更しない~~
  → **2026-09-23 撤回**。モックは pair / solo で出し分ける（§1-D）。土台と配線が無変更なのは変わらない。

### 1-B. 書き込み UX は現状維持（no-op 成功）（🟢）

- 登録・編集・削除は従来どおり `withDemoWriteVoid` で **no-op（成功トーストは出るが反映されない）**。
  DB アクセスなし。実装ゼロで最も安全。今回この挙動は変えない。

### 1-C. デモは「ペアあり / ペアなし」を**ログイン画面で選べる**（🟢）

- login 画面にデモボタンを **2 つ**置く: 「デモ（ペア）」「デモ（個人）」。
- 選んだ方に応じて**デモ Cookie に `pairId` を書き分ける**:
  - ペア → 固定モック `pairId`（例 `1`）を格納 → `session.pairId = 1`
  - 個人 → `pairId = null` を格納 → `session.pairId = null`
- `session` はデモ Cookie の値を読むだけ。URL 直叩きでも Cookie にモードが固定されるため一貫する。
- **理由**: アプリ内トグル方式（既存ペアモード＝共有 ON/OFF の Cookie）は「pairId の有無」とは別物で、
  デモ用に `session.pairId` 自体を切り替える別機構が要り実装が重い。ログイン時に確定する方が単純で堅い。
- **切り替わるのは `session.pairId` のみ**で、Supabase Auth のアカウントを 2 つ用意するわけではない
  （デモは Auth を一切使わないため「アカウント」という実体を持たない）。

### 1-D. デモモックを pair / solo で出し分ける（🟢 2026-09-23 追加）

当初は「モックは一切変更しない」前提だったが、既存モックを突合した結果**この前提では pair デモが成立しない**ため方針を変更する。

#### 変更の根拠（既存モックの実測）

全 feature の `demo.ts`（計 603 行）の `isPair` / `pair` を調べると、**ほぼ全てが個人（solo）データ**だった。

| feature | pair 側の現状 |
| :--- | :--- |
| [type-method](../nextjs/src/features/type-method/server/demo.ts) | `income.pair` / `pay.pair` / `both.pair` すべて `[]` |
| [plan-reminder](../nextjs/src/features/plan-reminder/server/demo.ts) | `pair: []`、全項目 `isPair: false` |
| [planned-record](../nextjs/src/features/planned-record/server/demo.ts) | `pair: []`、`pairUserName: null` |
| [summary](../nextjs/src/features/summary/server/demo.ts) | `pair: []`、`pairUserName: null`、全項目 `isPair: false` |
| [record](../nextjs/src/features/record/server/demo.ts) | `demoRecordList` / `demoSummarizedRecordList` は `isPair: false`・`pairUserName: null` |

ペア前提データは**例外的に 2 箇所だけ**存在する:

- `record/demo.ts` の `demoPairedRecordList`（立替 1 件 + 精算 1 件）… ペア機能の唯一のモック
- `memo-shortcut/demo.ts` の `isPair: true` のメモ 1 件 / `RecordType.pair` のショートカット 1 件

**この状態で pair デモを選ぶと何が起きるか**: `session.pairId = 1` になってペア UI（ペア切替スイッチ・
精算タブ・カテゴリ/方法のペア欄）が一斉に現れるのに、中身は `pair: []` で空。切替スイッチを ON にしても
カテゴリ 0 件、summary のペア集計も空になる。**「ペアありデモ」としての価値がほぼ無い。**

逆に solo デモでは `demoPairedRecordList`（立替・精算）が返る不整合が残る（詳細は §3-5・§5）。

→ **A案（モック共通・`session.pairId` だけ切替）は「両モードともデータが中途半端」な状態を固定化する**ため採らない。

#### 確定方針

- **pair デモ / solo デモでモックを出し分ける**。solo は「個人で使っている状態」、pair は「夫婦で共有して
  いる状態」（ペア相手名入りの共有レコード・立替・精算・ペアカテゴリが揃った姿）を見せる。
- **solo 側は現状のモックをそのまま流用できる**（ほぼ全て `isPair: false` のため）。新規作成はほぼ不要。
- **pair 側を追記する**。`pair: []` を埋め、`pairUserName` を持つ共有レコードを足す。
- **切り替えは mode 引数を全関数に配らない**。`session.pairId` が既に mode を反映しているため、
  サービス層は `withDemoRead` の第 2 引数で三項演算子を書くだけで済む:

  ```ts
  // 例: type-method/server/services.ts
  return withDemoRead(
    session.isDemo,
    session.pairId === null ? demoGroupedTypeListSolo : demoGroupedTypeListPair,
    async () => { /* 実処理は無変更 */ }
  );
  ```

  `withDemoRead` の**シグネチャ（凍結資産の土台）は変更不要**。各サービスの 1 行が変わるだけ。

#### トレードオフ（承知のうえで選択）

- **モック整合の責任が増える**: pair 側は `pairId` / `pairUserName` / `isPair` / `recordType`（5/10/15）が
  相互に整合していないと、精算金額の不一致などの見た目バグになる。特に summary の集計値と record の明細が
  食い違うと目立つ。→ 第 2 段階で実画面を見ながら詰める（§6）。
- **設計書 §4 の「非対象」を 1 つ動かす**: 「デモデータの拡充・整合改善は非対象」を撤回する。DB 非依存化
  という本題とは別軸の作業が入るため、**§6 の 2 段階構成でスコープ膨張を抑える**。

## 3. 実装時に詰める細部（🔵）

1. **固定 `SessionData` の中身**
   - `userUid`: 実在ユーザと衝突しない固定値（例 `'demo-user'`）。ただし `buildScopeWhere` はデモ経路では
     呼ばれない（取得はモックで早期分岐）ため scope 用途では使われない想定。値の妥当性を確認する。
   - `pairId`: pair モード時の固定値。**既存モックに `pairId` の参照は 1 件も無い**（2026-09-23 に全 `demo.ts` を
     grep して確認）ため、モック側との矛盾は構造上起きない。デモは DB に届かないため実データとの衝突は
     構造上起きず、**正値（例 `1`）でよい**（2026-09-23 に「デモの ID は負値」規約を廃止し、全モックを正の連番に統一済み）。
   - `email`: 画面表示（設定タブ等でメール表示があれば）用のダミー。実在 email を使わない。
2. **デモ Cookie の属性**: `httpOnly` + `sameSite=lax` + `secure`（本番）+ 有効期限（例 数時間〜1 日）。
   署名（HMAC）で改ざん検知。値は `{ mode, exp }` 程度で最小限。
3. **`getSessionData` の分岐順序**: React `cache()` メモ化は現状どおり維持。デモ分岐を最優先に置き、
   デモでない場合のみ Supabase 経路へ落ちる（現状の I/O 往復はデモでは完全にスキップされる）。
4. **proxy とデモ Cookie の検証共有**: proxy（Edge/proxy ランタイム）と Server Component 双方でデモ Cookie を
   検証するため、検証ロジックは `demoSession.ts` に集約しつつ **`server-only` を付けない**（proxy から使うため。
   supabaseProxy.ts と同じ判断）。あるいは proxy は「Cookie 存在＋署名検証」の軽量チェックのみに留める。
5. **既存モックがペア前提か個人前提かの確認** → **2026-09-23 に調査完了。結論は §1-D**。
   実測の結果、既存モックは**実質 solo 用データ**（`pair: []` / `isPair: false` が大半）であり、
   不整合の具体例は次の 1 箇所に特定できた:

   ```ts
   // record/server/services.ts:55  getPairedRecords
   return withDemoRead(session.isDemo, demoPairedRecordList, async () => {
     if (session.pairId === null) { return []; }   // ← デモはここに到達しない
     return recordRepo.getPairedRecordList(session, yearMonth);
   });
   ```

   デモ判定が `pairId === null` チェックより**先**にあるため、solo デモでも立替・精算モックが返る。
   [summary/page.tsx](../nextjs/src/app/(private)/summary/page.tsx) が `isExistPair` で先に弾くため画面には出ないが、
   データとしては矛盾しているので §2 #9 で直す。
6. **solo デモでペア切替スイッチが消える（仕様確認）**: [(private)/layout.tsx](../nextjs/src/app/(private)/layout.tsx) の
   `isExistPair = session.pairId !== null` が [PairModeSwitch](../nextjs/src/features/layout/components/pair-mode-switch.tsx) の
   表示を制御している。**solo デモではスイッチが出ない**。設計意図どおりなら対応不要だが、
   「デモでペア切替機能も見せたい」なら pair デモを既定（ボタンの並び順で誘導）にする判断が要る。
7. **`sessionSecret` はこのリポジトリで初の利用者になる**: [env.server.ts](../nextjs/src/lib/server/env.server.ts) の
   `required('SESSION_SECRET')` は**定義のみで参照ゼロ**（grep 確認済み）。既存の [getPairMode](../nextjs/src/lib/server/pair/mode.ts) の
   Cookie も署名なしの生値のため、**署名付き Cookie のパターン自体が前例なし**。Node の `crypto.createHmac` で
   新規に書くことになる（＝流用元が無い点を見込んでおく）。
8. **デモ無効環境**: `DEMO_USER_EMAIL` 未設定時はデモボタンを出さない（現状踏襲）。判定は server から
   props で渡すか、Server Action 側でガードする（現状の `demoUnavailable` トースト流儀を踏襲）。
   ボタンが 2 つになるため、無効時は**両方**出さない。

## 4. この変更で担保されること / されないこと

- **担保**: デモの全経路で Supabase Auth・DB へアクセスしない（認証も含めてゼロ）。実在アカウント/パスワード運用が不要。
- **担保**: `withDemoRead` / `withDemoWriteVoid` の土台（凍結資産）と各サービスの配線構造はそのまま活きる。

## 6. 進め方（2 段階構成・🟢 2026-09-23 決定）

§1-D で pair モックの充実を方針に入れた結果、本タスクは「DB 非依存化（認証基盤）」と
「デモデータの整備（ドメイン）」という**別軸の 2 つ**を含むことになった。一括で進めるとスコープが
膨らみレビュー単位も大きくなるため、**2 段階に分けて進める**。

### 第 1 段階: DB 非依存化（本題・単独で完結させる）

**目的**: 「デモは Supabase Auth・DB に一切アクセスしない」ゴールの達成。

**含むもの**: §2 の #1〜#9（デモ Cookie / session 早期 return / login ボタン 2 つ / proxy 分岐 /
ログアウト破棄 / env 整理 / 色マスタガード / `getPairedRecords` 分岐順）。

**この段階完了時点の状態**:

- デモの全経路で DB / Auth アクセスがゼロになる（**本タスクのゴールは達成済み**）
- pair デモを選ぶとペア UI は出るが中身は空（`pair: []` のまま）。**見栄えは未完成**
- solo デモは現状のモックで整合が取れており、そのまま見せられる

**ここで一旦区切る理由**: DB 非依存化は「不特定多数に公開する」ための**前提条件**であり、
セキュリティ/コスト面の要求を先に満たす。デモの見栄えは後から足せる。

### 第 2 段階: pair モックの充実

**目的**: pair デモを「夫婦で共有している状態」として見せられるようにする。

**含むもの**: §2 の #10（各 feature の `demo.ts` に pair 側データ追記 + サービス層の三項演算子化）。

**第 1 段階の後に回す理由**: 動くものを見ながらデータを足せるため、**モック間の整合を画面で確認できる**。
先にデータだけ作ると、金額の不一致や `recordType` の取り違えが実画面に出るまで気づけない。

### 一括で進める選択肢について

第 1・第 2 段階を 1 セッションで通すことも成立する（依存関係は第 1 → 第 2 の一方向のみ）。
ただし次の点で 2 段階を推奨する:

- 第 1 段階は**認証基盤の凍結資産**の改定、第 2 段階は**ドメインレーン**のモック追記で、
  所有レーンと必要な承認が異なる（§2 の注記）
- 第 1 段階だけでもゴール（DB 非依存）を満たすため、**途中で止まっても価値が残る**

### 採ってはいけない選択肢（記録として残す）

**A 案（モック共通・`session.pairId` だけ切替、pair モックを足さない）は採用しない。**
pair デモがペア UI だけ出て中身が空、という状態を「完了」として固定化してしまうため（根拠は §1-D）。
第 2 段階を省略する判断をする場合は、**pair デモボタン自体を出さない**（solo デモのみ提供する）ほうが、
中身が空のペアデモを見せるよりデモとしての体裁が保てる。
