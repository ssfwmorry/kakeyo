# かけよ 移行方針確定書（Vue/Nuxt → React/Next.js）

- **作成日**: 2026-09-21
- **対象**: 「かけよ」（個人・ペア向け家計簿 PWA）の Vue/Nuxt から React/Next.js への全面移行
- **位置づけ**: 移行に着手する前に「決めておくべき論点」を洗い出し、方針を確定した合意文書。
  ライブラリ個別の選定根拠は [カレンダーライブラリ選定.md](カレンダーライブラリ選定.md) / [グラフライブラリ選定.md](グラフライブラリ選定.md) を参照。

### 2.1 バンドラを Turbopack にする理由

新規構築のため、Next.js 標準の **Turbopack** を dev・build とも採用する。

- **dev は Stable**: Next.js 15 で `next dev --turbopack` は安定版に到達し、`create-next-app` でも既定で提示される。起動・HMR が webpack より大幅に速く、段階移行（§9）で新旧を何度も往復する本移行の開発体験に効く。
- **今後の標準**: Next.js/Vercel は Turbopack を今後の標準として投資しており、新規で webpack を選ぶ積極的な理由が乏しい。
- **build も実用段階**: `next build --turbopack` も stable 化が進んでおり、本アプリは特殊な webpack loader/plugin に依存しないため適用できる。
- **フォールバック方針**: 万一 Turbopack 非対応の loader/plugin や `next.config` の `webpack:` カスタムが必要になった場合に限り、その機能だけ webpack ビルドへ戻す（`--turbopack` を外す）。現時点で該当なし。

## 3. データアクセス層の方針

現状は FE が anon key で Supabase を直接叩き、RLS は `anon` に `using (true)` の全許可、認証は Firebase 側で担保という構成。
移行後は **BE（Server）から Prisma でラップ**し、FE から DB を直接叩かない。

### 3.1 RLS / 権限モデル

- Prisma は DB 直結のため **RLS をバイパスする**。ペア家計簿の「自分と共有相手のデータだけ見える」制御を**アプリ層で保証**する。
- 全クエリを、**認証済み `userUid` と `pairId` を必ず受け取る共通リポジトリ層**に通す。
  既存 RPC の絞り込み条件 `user_id = 自分 OR pairs.user1_id = 自分 OR pairs.user2_id = 自分` を、Prisma の共通 where ヘルパとして 1 箇所に集約する。
- Supabase 側の RLS は「万一の直アクセス」への多層防御として残す（`service_role` は使わず DB 直結）。

### 3.2 RPC（20 個）の移植方針

RPC を性質で 3 グループに分けて扱う。

| グループ | 対象 | 移植方針 |
| :--- | :--- | :--- |
| **A. 単純取得系（9）** | `get_type_list` / `get_method_list` / `get_plan_type_list` / `get_planned_record_list` / `get_plan_list` / `get_record_list` / `get_summarized_record_list` / `get_paired_record_list` / `get_sub_type_summary` | **Prisma ORM（`include`/リレーション）へ移植**。型が付き、リスクが小さい |
| **B. swap 系（5）** | `swap_method` / `swap_type` / `swap_sub_type` / `swap_plan_type` / `swap_planned_record` | **Prisma `$transaction`** で 2 行の sort を入れ替え（トランザクション必須） |
| **C. 集計系（6）** | `get_month_sum` / `get_type_summary` / `get_method_summary` / `get_pay_and_income_list` / `get_type_summary_period` / `post_records` | **`$queryRaw` で既存 SQL を TS ファイル内へ移植** |

**グループ C を `$queryRaw` にする理由**:
`record_type`（0/5/10/15）× is_pay × ペア関係 × 精算/立替の緻密な `CASE WHEN` は、このアプリのドメインの核心であり、
仕様が SQL の中にしか書かれていない。ORM の `groupBy` では精算の非対称な扱い（自分→受取は +、相手→受取は −）を表現しきれず、
TS へ「翻訳」するとバグの温床になる。**SQL をそのまま TS 内へ持ち込むことで、RPC デプロイの手間を無くしつつ家計の数字がズレない**ようにする。

> `post_records` は集計系に分類しているが、実体は「定期レコードの実体化 INSERT」であり、実行タイミングを §7 で再設計する。

## 4. DB / ドメインの方針

- **schema.prisma を正として DB を作り直す**（＋既存データの移行）。
- **PK は連番 int を維持**（`Id = number`、全結合キー・型定義に波及するため UUID 化しない）。
- **タイムゾーン**: 現行の「`Date` に +9 時間して `toISOString()` で切る」独自 JST 変換は廃止。
  SSR ではサーバー（Vercel は UTC）とクライアントで時刻がズレるため、**dayjs + utc/timezone plugin で `Asia/Tokyo` を明示**し、日付境界（`YYYY-MM-DD` 文字列）で一貫して扱う。
  「今日の日付」は全機能の起点なので、ここは移行の要注意ポイント。

## 5. 認証の方針

- Firebase Auth → **Supabase Auth へ移行**（skill-kick の Supabase Auth + Cookie セッション実装を参考にできる）。
- Firebase Auth の UID（`users.uid`、char(28)）が Supabase Auth の UID に変わるため、
  **`records.user_id` / `pairs.user1_id` / `pairs.user2_id` / 各テーブルの `user_id` などを新 UID へ付け替える**データ移行が必要。
- ログイン状態は **Cookie セッション**で保持（Pinia の persist は廃止）。

## 6. PWA の方針

要件は「**ホーム画面追加・全画面表示（installable + standalone）がメイン**」「**将来プッシュ通知も入れたい**」。オフライン対応・apk 配布は要件外。

| やること | 実装 | 時期 |
| :--- | :--- | :--- |
| ホーム画面追加・全画面表示 | **App Router 標準の `app/manifest.ts`**（`display: standalone`、アイコン、theme_color 等）。プラグイン不要 | 今 |
| インストール要件の充足 | manifest + アイコン（192/512）+ HTTPS（Vercel で自動）+ **最小 Service Worker（将来 Push の受け皿）** | 今 |
| プッシュ通知 | Web Push（VAPID）。SW + 通知許可 + 購読管理 | **将来**（土台のみ今作る） |

> オフラインキャッシュ目的の `@ducanh2912/next-pwa`（Workbox）は**採用しない**。オフライン不要・Push は将来のため、
> 依存を増やさず制御しやすい「素の manifest.ts + 軽量 SW」を選ぶ。

## 7. 定期レコード実体化（`post_records`）の再設計

### 7.1 現状の問題

現行 `useCalendarStore.updateRange` は、カレンダー表示のたびに以下を**まとめて**実行する。

1. `postRecords` — **未登録の定期レコードを DB に INSERT（副作用・書き込み）**
2. `getMonthSum` / `getRecordList` / `getPlanList` / `getReminderList` — 表示用データ取得（読み取り）

SSR（App Router）では、表示のためのサーバーコードが**プリフェッチ・並行レンダリング・再検証**で 1 操作あたり複数回実行されうる。
書き込み（1）が表示コードに混ざっていると、**多重 INSERT の危険**がある。SSR の原則「GET（表示）は副作用を持たせない／書き込みは明示的なアクションのみ」に反する。

### 7.2 確定した再設計

定期（＝固定費）は「ユーザーが何もしなくても正しい月に自動計上されてほしい／手動の確定・編集はしたくない」という要件。これを満たすため:

- **定期の実体化は Vercel Cron（日次 1 回）で自動実行**する。
  現行 `post_records` の SQL ロジックを Route Handler + Prisma（`$queryRaw`）で流用し、全ユーザーの未登録分を INSERT。
- **カレンダー表示は純粋な読み取りのみ**とし、表示コードから副作用 INSERT を排除する（多重 INSERT 問題を根本解決）。
- ユーザーによる定期の確定・編集操作は不要（自動計上）。

**Vercel Cron のコスト**: Hobby（無料）プランで **Cron 2 個まで・日次 1 回まで**。本件は「固定費を日次 1 回 INSERT」なので**無料枠で足りる**。
実行時刻が数時間ずれうる仕様だが、固定費実体化は「その日のうちに 1 回走れば十分」なので実害なし。
将来頻度が窮屈になれば Pro プラン、または GitHub Actions スケジュール / Supabase pg_cron が代替候補（今は決めない）。

## 8. その他の設計方針

- **ペアモード（共有 ON/OFF）**: **Cookie で保持し、トグルで再 fetch**（全画面共通の素直な設計）。
  「見えるデータのスコープが変わる切替」なので、両方のデータを持って出し分けるより、状態とデータが 1:1 に対応する再 fetch の方が責務が明快でバグが入りにくい。
  データ量も小さく頻度も低いため、設定画面を含め毎回 fetch して問題ない。
  現行の `pagesWithoutPair`（calendar / records / bank ＝個人専用でペア切替を出さない）区分は踏襲する。
- **クライアント状態管理**: 認証・ペアは Cookie。UI 状態（ローディング等）は **Zustand**。トーストは **sonner**。
- **デモログイン**: 現行の `if (isDemoLogin) return DEMO_DATA...` の散在を解消し、
  **Server 層でデモユーザー判定時にモックリポジトリを注入**する形へ集約（取得系は読み取り専用データ、更新系は no-op）。
- **`useRouterParamStore`**（画面間の大きいオブジェクト受け渡し）: **廃止**し、URL パラメータ + Server 再取得へ置換。
- **エラー監視（Sentry）**: 当面**不要**（Vercel 標準ログのみ）。
- **inquiry 画面**: 静的のまま移植。

## 9. 移行の進め方

- **別ディレクトリ（新規プロジェクト）で構築**し、現行 `kakeyo/`（Nuxt）は残す。
- DB は同一 Supabase を指し、認証移行（§5）が済んだ段階で切り替える。
- 画面は段階移行（例: calendar → note → summary → records → plan → bank → setting）。各段階で新旧を比較する。

### フェーズ案

| フェーズ | 内容 |
| :--- | :--- |
| 0. 基盤 | Next.js + pnpm + Biome + Shadcn + Prisma の雛形。`schema.prisma` を Prisma introspect で起こして確認 → 正として整備 |
| 1. 認証 | Supabase Auth + Cookie セッション。Firebase UID → Supabase UID のデータ移行 |
| 2. データアクセス層 | 共通リポジトリ層（認証絞り込み集約）。RPC-A / B / C の移植（§3.2） |
| 3. 画面移植 | Shadcn + FullCalendar + Recharts で画面単位に移植。ペアモード（Cookie）対応 |
| 4. 定期実体化 | Vercel Cron で `post_records` 相当を日次実行（§7） |
| 5. PWA / 仕上げ | `manifest.ts` + 最小 SW、Storybook、Vitest（ドメイン計算）、Vercel デプロイ |
