- **作成日**: 2026-09-21
- **対象**: 「かけよ」（Nuxt/Vue → Next.js App Router）の全面移行を、**複数 AI エージェントが同時並行**で実装するための作業手順書。
- **前提文書**:
  - 方針は [移行方針確定書.md](移行方針確定書.md) を正とする（技術選定・設計判断はここで確定済み。本書は「誰が・何を・どの順で・どう衝突なく作るか」の実行計画）。
  - 既存仕様は [../new/docs/replace/summary.md](../new/docs/replace/summary.md)（FE/BE 仕様書）を正とする。
  - DDL/RPC の SQL 実体は [../docs/database/](../docs/database/tables.md) を正とする。
  - 参考実装は `kakeyo/../skill-kick`（React Router v7 だが、Supabase Auth + Cookie / Prisma モデル層 / Shadcn / ドメイン構造の**書き方の参考**。App Router 流に読み替える）。

## 0. この手順書の使い方（オーケストレータ向け）

本書は **1 人のオーケストレータ（あなた or 統括エージェント）が読み、各実装エージェントに §7 の「作業指示書テンプレ」を配布する**前提で書かれている。

### 確定した並行実装の設計方針（本セッションで合意済み）

| 論点 | 確定 |
| :--- | :--- |
| schema.prisma の確定 | **Phase 0 で確定させ、以降の全エージェントの不変前提とする**（誰も schema を勝手に変えない） |
| 認証の順序 | **認証（Phase 1）を先行確定 → その後ドメイン並行**（全リポジトリ層が認証基盤に依存するため） |
| 並行の分割単位 | **ドメイン（機能）単位で縦割り**（モデル層＋サービス層＋画面を 1 エージェントが縦に担当） |
| 統合方式 | **git worktree で分離 → PR 統合**。共有ファイルは先に確定させ、以降は原則触らせない |
| 集計検証 | **ドメイン計算の Vitest のみ**（旧 RPC との自動照合はしない） |

### 鉄則（並行作業を破綻させないための 5 原則）

1. **共有ファイルは「凍結資産」**（§4）。凍結後にドメインエージェントが編集してはならない。変更が必要なら必ずオーケストレータに差し戻す。
2. **各ドメインエージェントは自分の担当ディレクトリ（§5 の所有境界）以外に書き込まない。**
3. **依存の順序を守る**（§3 の依存グラフ）。前提フェーズが「完了・マージ済み」になるまで後続を start しない。
4. **schema.prisma を勝手に変えない。** 追加カラムが要ると気づいたら止めてオーケストレータへ。
5. **各 PR は独立して型チェック（`tsc`）と Biome を通ること。** 通らない PR はマージ対象外。

## 2. フェーズ構成と並行度

移行は **直列フェーズ（0→1）→ 並行フェーズ（2〜4 をドメインごとに縦割り）→ 直列仕上げ（5）** の 3 段構え。

| フェーズ | 内容 | 並行度 | 担当 |
| :--- | :--- | :--- | :--- |
| **P0. 基盤** | Next.js 雛形 / pnpm / Biome / Tailwind+shadcn / Prisma / schema.prisma 確定 / 共有型・凍結資産の骨組み | **単独**（1 エージェント） | 基盤エージェント |
| **P1. 認証基盤** | Supabase Auth + Cookie セッション / `getSessionData` / 共通 where ヘルパ / middleware ガード / デモ注入の土台 | **単独**（1 エージェント、P0 完了後） | 認証エージェント |
| **P2〜4. ドメイン縦割り** | ドメインごとに「リポジトリ層＋サービス層＋画面」を縦に実装。定期実体化 Cron 含む | **並行**（ドメイン数だけ。§6 で 8 レーン） | ドメインエージェント ×N |
| **P5. 仕上げ** | 全画面レイアウト統合 / PWA(manifest+SW) / Storybook / Vercel デプロイ / DB マイグレーション + 手作業 UID 付け替え | **単独 or 少数**（全並行マージ後） | 仕上げエージェント |

## 3. 依存グラフ（start 可否の判定表）

各作業は「前提が全てマージ済み」になって初めて start してよい。

```
P0 基盤・schema確定・凍結資産の骨組み
   │  (完了・マージ後)
   ▼
P1 認証基盤（getSessionData / requireAuth / 共通whereヘルパ / デモ注入の土台）
   │  (完了・マージ後 = 全ドメインの前提)
   ▼
 ┌───────────────── ここから並行（ドメイン縦割り） ─────────────────┐
 │ L1 マスタ    L2 record  L3 定期+Cron  L4 type/method             │
 │ L5 plan/reminder  L6 summary/records  L7 bank  L8 memo/shortcut  │
 └──────────────────────────────────────────────────────────────┘
   │  (全レーンのPRがマージ後)
   ▼
P5 仕上げ（レイアウト統合 / PWA / Storybook / デプロイ / DBマイグレーション）
```

### ドメインレーン間の依存（重要：これが縦割りの衝突源）

ドメインは完全独立ではない。**下記の「参照関係」は、被参照側の型・リポジトリを先に確定させることで解消する。**

| レーン | 依存（＝被参照）するもの | 解消策 |
| :--- | :--- | :--- |
| L2 record | L4 type/method/subType（record は type_id/method_id を持つ） | L4 の**リポジトリ I/F と型を先に確定**（§4.2 の型凍結）。実装本体は並行可 |
| L3 定期+Cron | L2 record（post_records は records を INSERT）/ L1 dayClassification | record リポジトリの insert I/F を凍結。Cron の集計 SQL は §3.2-C を $queryRaw で移植 |
| L6 summary/records | L2 record（集計 RPC 群）/ L4 type/method | 集計サービスは record リポジトリ経由。型を凍結すれば並行可 |
| L5 plan/reminder | L1 color / plan_type（同レーン内）/ reminder→plan 生成 | レーン内で完結（plan と reminder は同一エージェント） |
| L7 bank | L1 color のみ | ほぼ独立 |
| L8 memo/shortcut | L1 color / L4 type・method（shortcut が参照） | 型凍結で並行可 |

> **縦割りの肝**: レーン間参照は「実装」ではなく「**型と I/F の凍結**」で切る。被参照側の関数シグネチャと戻り型を Phase 1 の終わりまでに `lib/types/` と各リポジトリの I/F として先に置いておけば、中身は並行実装できる。

## 4. 凍結資産（共有ファイル）— 誰が作り、いつ凍結するか

並行作業の衝突は「複数エージェントが同じファイルを触る」ことで起きる。それを防ぐため、共有物は **Phase 0/1 で確定→凍結**し、ドメインエージェントは**読むだけ**にする。

### 4.1 Phase 0 で凍結する資産（基盤エージェント）

| 資産 | パス | 内容 | 凍結後の扱い |
| :--- | :--- | :--- | :--- |
| Prisma スキーマ | `prisma/schema.prisma` | 既存 `docs/database/tables.md` から起こす。**PK は連番 int 維持**、UID は Supabase Auth 前提で見直し（§5 認証）。`prisma db pull` の結果を叩き台にしつつ、確定版として整備しレビュー | **完全凍結**。変更はオーケストレータ承認必須 |
| Prisma client | `lib/db/client.ts` | シングルトン。`@prisma/adapter-pg` で DB 直結 | 凍結 |
| 設定一式 | `next.config.ts` / `biome.json` / `tsconfig.json` / `tailwind.config` / `components.json` | Turbopack（dev/build）、pnpm、Biome、shadcn 初期化 | 凍結（P5 で最終調整） |
| shadcn UI | `components/ui/*` | 使う shadcn コンポーネントを一括生成（button/dialog/tabs/select/input/sonner/chart 等） | 凍結（追加が要れば個別に追加のみ、既存は触らない） |
| 環境変数定義 | `lib/env.ts` / `.env.example` | Supabase URL/anon/service、セッション秘密鍵等の型付き読み出し | 凍結 |

### 4.2 Phase 1 で凍結する資産（認証エージェント）

| 資産 | パス | 内容 | 凍結後の扱い |
| :--- | :--- | :--- | :--- |
| Supabase Auth | `lib/auth/supabase.ts` | `@supabase/ssr` で Cookie ベースのサーバクライアント（skill-kick `supabase.server.ts` 相当） | 凍結 |
| セッション | `lib/auth/session.ts` | `getSessionData(cookies)` → `{ userUid, pairId, email, isDemo }`。Cookie セッション読み書き | 凍結 |
| 認証ガード | `lib/auth/requireAuth.ts` | Server Component/Action で「未ログインなら redirect(/login)」。middleware も設置 | 凍結 |
| **共通 where ヘルパ** | `lib/db/scope.ts` | **本移行の心臓**。`buildScopeWhere({ userUid, pairId })` = 既存 RPC の `user_id = 自分 OR pairs.user1_id = 自分 OR pairs.user2_id = 自分` を Prisma where に 1 箇所集約（方針書 §3.1） | **完全凍結**。全リポジトリがこれを通す |
| デモ注入土台 | `lib/auth/demo.ts` | デモユーザ判定時にモックリポジトリを注入する仕組みの骨組み（方針書 §8）。取得=読み取り専用データ、更新=no-op | 骨組み凍結、各ドメインが自分のモックを足す |
| 共有ドメイン | `lib/domain/recordType.ts` / `lib/domain/date.ts` | record_type(0/5/10/15) 判定・算出、dayjs+utc/timezone で `Asia/Tokyo` 日付境界（方針書 §4）。**Vitest 付き** | 凍結（ドメイン計算の単一の正） |
| 共有型 | `lib/types/*.ts` | 全ドメインが参照する ID 型（`Id = number`）、`ApiResult`、record_type enum、認証パラメータ型など | 凍結 |
| レーン間 I/F 型 | 各リポジトリの型定義（§3 の被参照側） | L4 type/method、L2 record など「他レーンから参照される」リポジトリの**関数シグネチャと戻り型のスタブ**を先に置く | 凍結（中身は各レーンが実装） |

> **Phase 1 の追加責務**: ドメインレーン間参照（§3 の表）を切るため、**被参照リポジトリの I/F（型だけの空実装 or interface）を先に置く**。これがあるとドメインエージェントは「相手の実装を待たずに型に対してコードを書ける」。

## 5. ドメインエージェントの所有境界（書き込み許可ディレクトリ）

各ドメインエージェントは **自分のレーンのファイルにのみ書き込む**。下表以外は読むだけ。

| レーン | 書き込み可（所有） | 読むだけ（凍結資産） |
| :--- | :--- | :--- |
| 各ドメイン共通 | `lib/repositories/<domain>.ts` / `lib/services/<domain>.ts` / `app/(private)/<screen>/**` / `components/<domain>/**` / 各 `*.test.ts` | `prisma/schema.prisma` / `lib/db/*` / `lib/auth/*` / `lib/domain/*` / `lib/types/*` / `components/ui/*` |

- 画面ルートは App Router の route group `app/(private)/calendar/page.tsx` のようにレーンごとにディレクトリが分かれるため衝突しない。
- **共通レイアウト（ボトムナビ・ペア切替スイッチ・リマインダー通知）は P5 の仕上げエージェントが統合**する。各ドメインエージェントは自画面の中身に集中し、レイアウト shell には触らない（衝突源になるため）。
- ルート登録（App Router はファイルベースなので基本自動だが、`app/(private)/layout.tsx` のような共有 layout は凍結資産扱い、P1 で骨組みを置く）。

## 6. ドメインレーンの割り当て（8 レーン）

方針書の RPC 3 グループ（A 単純取得 / B swap / C 集計）と画面仕様を、縦割りに再編成する。

| レーン | ドメイン | リポジトリ/サービス | 画面 | 移植する RPC/API（方針書 §3.2） |
| :--- | :--- | :--- | :--- | :--- |
| **L1** | マスタ | color_classification / day_classification / user / pair | （画面なし。全レーンの土台） | `getColorClassificationList` / `getDayClassificationList` / `getPairId`（テーブル直） |
| **L2** | record（中核） | record リポジトリ / 取得系サービス | note（記録入力の record 部分） | A: `get_record_list` / `get_summarized_record_list` / `get_paired_record_list`。CRUD: `upsertRecord` / `createSettlementRecord` / `settleRecords` / `deleteRecord` |
| **L3** | 定期＋Cron | planned_record リポジトリ / 実体化バッチ | note（定期部分）/ setting 定期タブ | A: `get_planned_record_list`。B: `swap_planned_record`。**C: `post_records` を Vercel Cron 化**（方針書 §7） |
| **L4** | type/method | type / sub_type / method リポジトリ | setting 家計管理タブ（KakeiType/KakeiMethod）| A: `get_type_list` / `get_method_list`。B: `swap_type` / `swap_sub_type` / `swap_method`。CRUD 各 upsert/delete |
| **L5** | plan/reminder | plan / plan_type / reminder / condition | plan 画面 / setting 予定管理タブ | A: `get_plan_list` / `get_plan_type_list`。B: `swap_plan_type`。CRUD: upsertPlan/reminder 系（2 テーブル跨ぎの insert/delete/check） |
| **L6** | summary/records | 集計サービス（$queryRaw） | summary 画面（4 タブ）/ records 明細画面 | **C: `get_month_sum` / `get_type_summary` / `get_method_summary` / `get_type_summary_period` / `get_sub_type_summary` / `get_pay_and_income_list`**（$queryRaw で SQL 移植） |
| **L7** | bank | bank / bank_balance | bank 画面 / setting 口座タブ | CRUD: getBankList/upsertBank/deleteBank/getBankBalanceList/postBankBalances（テーブル直） |
| **L8** | memo/shortcut | memo / short_cut | calendar 内 TODO・ショートカット | CRUD: getMemoList/insertMemo/deleteMemo/getShortCutList（テーブル直） |

### calendar 画面と login 画面の扱い（跨りレーン）

- **calendar（ホーム）**は record・plan・reminder・memo・shortcut を横断表示するため、**P5 直前に「calendar 統合レーン」として、L2/L5/L8 のサービスを組み合わせる**（各サービスが揃ってから）。方針書 §7 の通り**表示は純粋な読み取りのみ**（副作用 INSERT は L3 の Cron に完全移譲）。
- **login 画面**は認証エージェント（P1）が担当。`getPairId` 呼び出し（→ Cookie に pairId 格納）まで含める。
- **inquiry** は静的移植（P5 の仕上げに含める）。

### 7.0 共通ヘッダ（全エージェント共通で先頭に付ける）

```
あなたは「かけよ」Nuxt→Next.js 移行の実装エージェントです。
- 作業ディレクトリ: kakeyo/nextjs（git worktree: <branch名> で分離済み）
- 必読: migration-plan/移行方針確定書.md（設計判断の正）/ 移行手順書.md（本書）
- 仕様の正: new/docs/replace/*.md と docs/database/*.md
- 参考実装: ../skill-kick（App Router 流に読み替える。丸写ししない）
- 鉄則:
  1. 凍結資産（prisma/schema.prisma, lib/db/*, lib/auth/*, lib/domain/*, lib/types/*, components/ui/*）は読むだけ。編集が要れば止めて報告。
  2. 自分の所有ディレクトリ（下記）以外に書き込まない。
  3. schema.prisma は絶対に変えない。カラム不足に気づいたら止めて報告。
  4. 完了条件: `pnpm biome check` と `pnpm tsc`（typecheck）が通ること。該当すれば Vitest も。
  5. CLAUDE.md（skill-kick 由来のコーディング規約：CRUD 順・早期 return・マジックナンバー禁止・コメント方針）に従う。
```

### 7.1 P0 基盤エージェント指示

```
目的: kakeyo/nextjs に Next.js(App Router)+pnpm+Biome+Tailwind/shadcn+Prisma の雛形を作り、
      §4.1 の凍結資産をすべて確定させる。
やること:
1. create-next-app（App Router, TS, Turbopack, pnpm）で kakeyo/nextjs を初期化。
2. Biome / Tailwind / shadcn 初期化。§4.1 に列挙の shadcn コンポーネントを一括生成。
3. docs/database/tables.md を正として prisma/schema.prisma を作成。
   - PK は連番 int 維持（Id=number）。全テーブル（users/pairs/methods/types/sub_types/records/
     planned_records/plans/plan_types/conditions/reminders/memos/short_cuts/banks/
     bank_balances/day_classifications/color_classifications）を網羅。
   - users.uid は現状 Firebase UID(char28)。Supabase Auth 移行前提だが、schema 上は可変長 string のまま。
     （実際の UID 付け替えは P5 のデータ移行で手作業。schema は変えない）
4. lib/db/client.ts（Prisma singleton, adapter-pg）/ lib/env.ts / .env.example を作る。
完了条件: pnpm dev が起動、prisma validate が通る、tsc/biome が通る。
成果を PR。オーケストレータがレビューし schema.prisma を「凍結」宣言する。
所有: kakeyo/nextjs 全体（初期化フェーズのため）
```

### 7.2 P1 認証エージェント指示

```
目的: §4.2 の認証・共有基盤を確定させ、ドメイン並行の前提を整える。
前提: P0 マージ済み。
やること:
1. lib/auth/{supabase.ts, session.ts, requireAuth.ts, demo.ts}（skill-kick の auth 実装を App Router 流に）。
   - getSessionData(cookies) → { userUid, pairId, email, isDemo }
   - middleware.ts で未ログインを /login へ、ログイン時 / → /calendar、/login → /note のリダイレクト（仕様書 §認証）
2. lib/db/scope.ts: buildScopeWhere({userUid,pairId}) = 既存絞り込み条件を Prisma where に集約（方針書 §3.1）。
3. lib/domain/{recordType.ts, date.ts} を Vitest 付きで実装（方針書 §4）。
   - recordType: 0/5/10/15 の判定・upsert 時の算出（!isPair→0 / isPair&&isInstead→5 / isPair&&!isInstead→10）
   - date: dayjs+utc/timezone で Asia/Tokyo。旧「+9h して toISOString」は廃止。YYYY-MM-DD 文字列で境界統一
4. lib/types/*: Id=number, record_type enum, 認証パラメータ型（SupabaseApiUser 等の後継）, ApiResult
5. login 画面（app/(auth)/login/page.tsx）: Supabase Auth ログイン/デモログイン/パスワード再設定 + getPairId→Cookie 格納
```

## 8. 統合（git worktree → PR）の運用

- 各エージェントは `kakeyo/nextjs` を対象に、レーンごとの worktree/ブランチで作業（例: `feat/nextjs-p0-base`, `feat/nextjs-l2-record`）。
- **マージ順序**: P0 → P1 →（L1〜L8 は任意順、ただし §3 の依存＝型凍結が満たされていること）→ P5。
- **コンフリクトが起きる唯一の現実的箇所**は「凍結資産への誤編集」と「共有 layout」。前者は鉄則で禁止、後者は P5 集約で回避。
- 各 PR のレビュー観点: ①凍結資産を触っていないか ②buildScopeWhere を通しているか（絞り込み漏れ＝情報漏洩リスク）③集計 SQL の CASE WHEN を改変していないか ④tsc/biome/Vitest。
- レビューには `mico-eng-basic:reviewer-*` エージェント群（security / architecture / code-quality）を活用可。

## 9. リスクと対策（並行実装特有）

| リスク | 影響 | 対策 |
| :--- | :--- | :--- |
| schema.prisma の後出し変更 | 全レーンが作り直し | P0 で徹底レビューして凍結。不足時はオーケストレータが一括改定し全レーンへ通知 |
| buildScopeWhere の絞り込み漏れ | ペアの他人データが見える（重大） | 凍結・単一実装・全リポジトリ経由を強制。security レビュー必須 |
| 集計 $queryRaw の数字ズレ | 家計が合わない | SQL を「翻訳せずそのまま移植」（方針書 §3.2-C）。ドメイン計算は Vitest。旧アプリと目視突合（P5） |
| レーン間の型待ち | 並行が直列化 | P1 で被参照リポジトリの I/F スタブを先置き（§4.2-7） |
| 定期の多重 INSERT | データ重複 | 表示から副作用を排除し Cron に一元化（方針書 §7）。表示コードは読み取りのみをレビューで担保 |
| JST 日付境界のズレ | 「今日」がズレて全機能に波及 | lib/domain/date.ts に集約＋Vitest。各レーンは自前で日付変換しない |
