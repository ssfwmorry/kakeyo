## 0. この手順書の使い方（オーケストレータ向け）

本書は **1 人のオーケストレータ（あなた or 統括エージェント）が読み、各実装エージェントに §7 の「作業指示書テンプレ」を配布する**前提で書かれている。

### 確定した並行実装の設計方針（本セッションで合意済み）

| 論点 | 確定 |
| :--- | :--- |
| schema.prisma の確定 | **Phase 0 で確定させ、以降の全エージェントの不変前提とする**（誰も schema を勝手に変えない） |
| 認証の順序 | **認証（Phase 1）を先行確定 → その後ドメイン並行**（全リポジトリ層が認証基盤に依存するため） |
| 並行の分割単位 | **ドメイン（機能）単位で縦割り**（モデル層＋サービス層＋画面を 1 エージェントが縦に担当） |
| 統合方式 | **git worktree で分離 → PR 統合**。共有ファイルは先に確定させ、以降は原則触らせない |
| 集計検証 | **ドメイン計算の Vitest のみ**（旧 RPC との自動照合はしない） |

### 鉄則（並行作業を破綻させないための 5 原則）

1. **共有ファイルは「凍結資産」**（§4）。凍結後にドメインエージェントが編集してはならない。変更が必要なら必ずオーケストレータに差し戻す。
2. **各ドメインエージェントは自分の担当ディレクトリ（§5 の所有境界）以外に書き込まない。**
3. **依存の順序を守る**（§3 の依存グラフ）。前提フェーズが「完了・マージ済み」になるまで後続を start しない。
4. **schema.prisma を勝手に変えない。** 追加カラムが要ると気づいたら止めてオーケストレータへ。
5. **各 PR は独立して型チェック（`tsc`）と Biome を通ること。** 通らない PR はマージ対象外。

## 1. 全体像（移行先ディレクトリ）

```
kakeyo/
├── (既存 Nuxt 一式：移行完了まで残す。触らない)
├── migration-plan/           ← 本書と方針書・選定書
└── nextjs/                   ← ★ ここに新アプリを全部作る

    │   │   ├── repositories/ ← ドメイン別リポジトリ層（Prisma ラップ）
    │   │   ├── services/     ← ドメイン別サービス層（集計・ドメインロジック）
    │   │   ├── auth/         ← Supabase Auth + Cookie セッション（凍結資産）
    │   │   ├── pair/         ← ペアモード Cookie（getPairMode/setPairMode。凍結資産）
    │   │   ├── flash.ts      ← 遷移をまたぐトーストの書き込み側（凍結資産）
    │   │   └── env.server.ts ← server 専用環境変数（凍結資産）
    │   └── shared/           ← ★ 両用（型・純粋関数・定数。FE/BE どちらからも安全）
    │       ├── types/        ← 共有型（凍結資産）
    │       ├── domain/       ← record_type/JST 日付/金額パースなど純粋ドメイン（凍結資産＋Vitest）
    │       ├── db/scope.ts   ← 共通 where ヘルパ（本移行の心臓。凍結資産＋Vitest）
    │       ├── auth/routes.ts← 認証パス定数（凍結資産）
    │       ├── toast/        ← flashCookie 定数（凍結資産）
    │       ├── env.ts        ← public 環境変数（凍結資産）
    │       └── utils.ts
    ├── components/
    │   ├── ui/               ← shadcn 生成物（凍結資産）
    │   ├── form/             ← フォーム標準（FormField/useFormToast 等。凍結資産）
    │   └── (domain 別)/
    ├── prisma/
    │   └── schema.prisma     ← ★ Phase 0 で確定させる最重要凍結資産

```

> **FE/BE 分離（P1 のリファクタで確定・凍結）**: `lib/` は「開いた時にディレクトリ名で境界がわかる」よう **`lib/server/`（BE 専用・`server-only`）** と **`lib/shared/`（型・純粋関数・定数の両用）** に二分する。ドメインが書く repositories/services は BE 専用のため `lib/server/` 配下。型・ドメイン計算・scope・定数は両用のため `lib/shared/` 配下。**Phase 0/1 で確定済み、以降固定。**

## 2. フェーズ構成と並行度

移行は **直列フェーズ（0→1）→ 並行フェーズ（2〜4 をドメインごとに縦割り）→ 直列仕上げ（5）** の 3 段構え。

| フェーズ | 内容 | 並行度 | 担当 |
| :--- | :--- | :--- | :--- |
| **P0. 基盤** | Next.js 雛形 / pnpm / Biome / Tailwind+shadcn / Prisma / schema.prisma 確定 / 共有型・凍結資産の骨組み | **単独**（1 エージェント） | 基盤エージェント |
| **P1. 認証基盤** | Supabase Auth + Cookie セッション / `getSessionData` / 共通 where ヘルパ / proxy ガード（旧 middleware）/ デモ注入の土台 | **単独**（1 エージェント、P0 完了後） | 認証エージェント |
| **P2〜4. ドメイン縦割り** | ドメインごとに「リポジトリ層＋サービス層＋画面」を縦に実装。定期実体化 Cron 含む | **並行**（ドメイン数だけ。§6 で 8 レーン） | ドメインエージェント ×N |
| **P5. 仕上げ** | 全画面レイアウト統合 / PWA(manifest+SW) / Storybook / Vercel デプロイ / DB マイグレーション + 手作業 UID 付け替え | **単独 or 少数**（全並行マージ後） | 仕上げエージェント |

## 3. 依存グラフ（start 可否の判定表）

各作業は「前提が全てマージ済み」になって初めて start してよい。

```
P0 基盤・schema確定・凍結資産の骨組み
   │  (完了・マージ後)
   ▼
P1 認証基盤（getSessionData / requireAuth / 共通whereヘルパ / デモ注入の土台）
   │  (完了・マージ後 = 全ドメインの前提)
   ▼
 ┌───────────────── ここから並行（ドメイン縦割り） ─────────────────┐
 │ L1 マスタ    L2 record  L3 定期+Cron  L4 type/method             │
 │ L5 plan/reminder  L6 summary/records  L7 bank  L8 memo/shortcut  │
 └──────────────────────────────────────────────────────────────┘
   │  (全レーンのPRがマージ後)
   ▼
P5 仕上げ（レイアウト統合 / PWA / Storybook / デプロイ / DBマイグレーション）
```

### ドメインレーン間の依存（重要：これが縦割りの衝突源）

ドメインは完全独立ではない。**下記の「参照関係」は、被参照側の型・リポジトリを先に確定させることで解消する。**

| レーン | 依存（＝被参照）するもの | 解消策 |
| :--- | :--- | :--- |
| L2 record | L4 type/method/subType（record は type_id/method_id を持つ） | L4 の**リポジトリ I/F と型を先に確定**（§4.2 の型凍結）。実装本体は並行可 |
| L3 定期+Cron | L2 record（post_records は records を INSERT）/ L1 dayClassification | record リポジトリの insert I/F を凍結。Cron の集計 SQL は §3.2-C を $queryRaw で移植 |
| L6 summary/records | L2 record（集計 RPC 群）/ L4 type/method | 集計サービスは record リポジトリ経由。型を凍結すれば並行可 |
| L5 plan/reminder | L1 color / plan_type（同レーン内）/ reminder→plan 生成 | レーン内で完結（plan と reminder は同一エージェント） |
| L7 bank | L1 color のみ | ほぼ独立 |
| L8 memo/shortcut | L1 color / L4 type・method（shortcut が参照） | 型凍結で並行可 |

> **縦割りの肝**: レーン間参照は「実装」ではなく「**型と I/F の凍結**」で切る。被参照側の関数シグネチャと戻り型を Phase 1 の終わりまでに `lib/shared/types/` と各リポジトリの I/F（`lib/server/repositories/`）として先に置いておけば、中身は並行実装できる。

## 4. 凍結資産（共有ファイル）— 誰が作り、いつ凍結するか

並行作業の衝突は「複数エージェントが同じファイルを触る」ことで起きる。それを防ぐため、共有物は **Phase 0/1 で確定→凍結**し、ドメインエージェントは**読むだけ**にする。

### 4.1 Phase 0 で凍結する資産（基盤エージェント）— ★ 実装完了・確定

> 手順書初版の想定（middleware / Radix ベース shadcn 等）から実装時点の最新へ更新済み。以降の全エージェントはこの版を不変前提とする。

### 4.2 Phase 1 で凍結する資産（認証エージェント）— ★ 実装完了・確定

> **実装時の重要な設計確定（セルフレビューを経て変更）**:
> 1. **セッションの真偽源をすべてサーバに一元化**。`getSessionData()` は `userUid`/`email` を Supabase `getUser()`（サーバ検証）から、`pairId` を `userUid` からの DB 照会（`getPairId`）から、`isDemo` を email 照合から**毎回導出**する。**pairId/isDemo をクライアント Cookie に持たせない**。← 当初は署名付きアプリ Cookie に pairId/isDemo を載せる設計だったが、署名は値の改ざんしか防げず「別ユーザの Cookie 残存による帰属ずれ（A の pairId が B のセッションに引きずられ他ペアデータ露出）」を防げないため廃止。pair は 1 ユーザ 1 件と軽量で毎回照会しても実害なし。
> 2. **middleware は Next.js 16 で `proxy.ts` にリネーム**（§7.2 の「middleware」は proxy に読み替え）。
> 3. **認証は 2 段（Supabase Auth の sb-* Cookie が真偽源 / アプリは Cookie を信用しない）**。

> **フォーム方針の凍結（全レーン共通）**: 入力フォームは **Conform + Zod + トースト通知** を標準とする（新パターンを発明しない）。
> - **スキーマ**: 各画面の `schema.ts` に Zod で定義。
> - **Server Action**: `parseWithZod`（`@conform-to/zod/v4`）で検証し、**`FormActionResult`（`{ submission, toast }`）を返す**。field/フォームエラーは `submission`（`submission.reply()`）、成否通知は `toast`（`{ type, message }`）に載せる。「action のレスポンスにトースト文言を埋め込む」skill-kick 流。
> - **クライアント**: `useForm({ lastResult: result.submission, onValidate })` + `components/form/FormField` でフォームを組み、`useFormAction`（`useActionState`+`useFormToast` 一体化）で action 結果の toast を**自動発火**する（各画面で `toast.xxx` を手書きしない）。「1 フォーム = 1 スキーマ = 1 useForm」。
> - トースト種別は success / error / info / warning（旧 Pinia トーストの後継）。成功→トースト、フィールド不正→インライン、が役割分担。

> **型の一本化（P1 のリファクタで確定）**: サービス層と Server Action の戻り型を整理し、重複変換を排した。
> - **サービス層（`lib/server/services/*`・リポジトリ）は `Result<T,E>`（`{ ok, data }` | `{ ok:false, error }`）を返す**。UI 文言は持たない（`error` は機械可読な分類）。
> - **Server Action が `toFormResult(result, { success, errorMessage })` で `FormActionResult` に変換**してトースト文言を付ける（`lib/shared/types/formResult.ts` に凍結。各レーンが変換を手書きしない）。
> - 旧 `ApiResult<T>`（UI 文言混在型）は廃止。`demo.ts` も `Result` ベース。

> **トースト2系統の使い分け（P1 で確定・全レーン遵守）**:
> - **遷移しないフォーム**（バリデーション失敗の再表示など）→ Server Action が `FormActionResult.toast` を返し、`useFormAction`/`useFormToast` が発火。
> - **`redirect()` を挟む Server Action**（保存後に一覧へ遷移など）→ 戻り値は遷移で消えるため、redirect 直前に `setFlashToast()`（`lib/server/flash.ts`）で Cookie に載せ、遷移先で `FlashToast`（root layout 常設）が消費・発火する。
> - CRUD の多くは「保存→遷移」型のため flash 側を使う場面が多い。二重発火を避けるためどちらか一方に統一する。

> **Phase 1 の I/F スタブ方針（判断軸を変更）**: 当初は「全被参照リポジトリの取得系・更新系 I/F を P1 で網羅的に凍結」を志向していたが、**取得系の戻り型（整形済み形状）は被参照レーンと参照レーンの設計に強く依存し、P1 時点で固めると誤凍結リスクが高い**。そのため P1 では **確実に他レーンが依存する最小の I/F のみ**を先置きする方針に変更した:
> - `record.ts`: `insertRecords`（L3 定期実体化が参照）+ `RecordInsertInput`
> - `type.ts` / `method.ts`: `getTypeList` / `getMethodList`（整形の最小形）
> - `dayClassification.ts`: `getDayClassificationList`（L3 が参照）
>
> **取得系の詳細 I/F（例: L6 が参照する record 集計の戻り型）は、その被参照レーンの実装初期にオーケストレータ承認のうえ追記する**（凍結資産の追記＝§9 リスク「レーン間の型待ち」との比較衡量で、誤凍結より遅延を選ぶ）。自己完結レーン（L5 plan/reminder, L7 bank）の I/F は各エージェントが自分で作る。

> **⚠️ BigInt PK の型境界（L2 record / L8 short_cut）**: `records` / `short_cuts` の PK は Prisma 上 `BigInt`。`BigInt` は `JSON.stringify` で例外を投げるため、Server→Client（props / Server Action 戻り値 / `useActionState` state）を跨ぐとクラッシュする。**I/F スタブの戻り型は `id: number` で凍結**し、リポジトリ／サービス層の境界で `Number(row.id)` へ変換する（方針確定書 §4.1）。変換責任を境界に集約し、各レーンが自前変換しない。

> **⚠️ 金額パース（金額カラムを持つ全レーン）**: `FormData` は全て文字列で届く。金額（`price: Int`）は共有パーススキーマ **`lib/shared/domain/price.ts`（`priceSchema` / `parsePrice`）**（Zod `z.coerce.number().int().nonnegative()` + カンマ／全角前処理・Vitest 付き）を経由する（方針確定書 §4.2）。素の `Number()` は使わない。

     → 旧「全 FK を新 UID へ一斉付け替え」より破壊が小さく、ロールバックも容易。
   - デモユーザも同様（Supabase Auth 作成 → supabase_user_uid 紐付け。`DEMO_USER_EMAIL` はその email）。
   - Supabase ダッシュボードで Email provider を有効化しておくこと（signInWithPassword の前提）。
完了条件: Vercel 本番で全画面動作、家計の数字が旧アプリと一致（目視確認）。
